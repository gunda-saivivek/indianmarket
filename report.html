3. Security Architecture: Stateless JWT & RBAC

Why Stateless JWT + BCrypt was Selected as the Best Security Model

In high-frequency trading platforms and institutional dashboards, low latency, horizontal scalability, and zero-trust perimeter security are paramount. The implementation avoids stateful cookie-based sessions in favor of Stateless JSON Web Tokens (JJWT 0.11.5) signed with HMAC SHA-256 for the following technical reasons:

  1. Stateless Clustered Scalability: Traditional session-cookie architectures require server-side session affinity (sticky sessions) or an external distributed cache (e.g. Redis) to share sessions across replicas. Stateless JWTs embed the user's identity and granted authorities directly in cryptographically signed claims, allowing any backend instance to validate requests independently.
  2. Complete Immunity to CSRF Attacks: Cross-Site Request Forgery exploits the automatic transmission of browser cookies. By passing tokens via the HTTP Authorization: Bearer <token> header, malicious cross-site scripts cannot hijack user sessions.
  3. Decoupled Microservice Readiness: Tokens can be verified by API gateways, WebSocket servers, or downstream microservices using only the shared HMAC key, without querying the database for every single request.
  4. Cryptographic Password Salting: Passwords are never stored in plaintext. They are encoded using BCryptPasswordEncoder(12) with an adaptive work factor of 12 rounds, providing resistance against GPU-accelerated brute force attacks.

As mandated by the prompt: "Employees/customers must not access admin APIs."
This is strictly enforced at two independent layers:
  1. Security Filter Chain Layer: .requestMatchers("/api/admin/**").hasRole("ADMIN") blocks non-admin requests before they reach the controller.
  2. Method Security Layer: @PreAuthorize("hasRole('ADMIN')") on AdminController executes secondary authorization checks at method execution time.

4. Relational Database Schema & Data Models

The data model enforces integrity through primary keys, foreign key constraints with cascading deletes, and unique indexes: 

-- 1. Roles Reference Table
CREATE TABLE roles (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);

-- 2. Users Table
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 3. Many-to-Many Join Table with Foreign Key Constraints
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id),
    CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    CONSTRAINT fk_role FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE CASCADE
);
